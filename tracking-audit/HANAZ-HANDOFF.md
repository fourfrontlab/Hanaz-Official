## Event map

Every event is opt-in. The browser module initializes one Pixel. Explicit event code replaces automatic inference; unrelated automatic activity is not characterized as inherently false.

| Event | Exact qualifying trigger | Source | Identifier/deduplication |
|---|---|---|---|
| PageView | A document view after consent/configuration, a genuine popstate route change, or restored bfcache view; not hash-only interactions | Browser | Fresh UUID per genuine view; one emission per document/route state |
| ViewContent | `loadProductDetail()` successfully fetches and renders an actual product | Browser | UUID for the rendered product view; UUID product ID and database sale price |
| AddToCart | Valid item/quantity successfully saved in `hanaz_cart` | Browser | Fresh action UUID; quantity and value represent the units added; failed storage emits nothing |
| InitiateCheckout | Checkout loads with a nonempty cart | Browser | One UUID per checkout document; actual cart quantities/subtotal; empty checkout emits nothing |
| Lead | Contact or newsletter request committed in `contact_messages` | Browser + server | Server-generated UUID, returned in accepted response; browser `eventID` equals server `event_id`, both named Lead |
| Purchase — COD | One server transaction creates the accepted order, authoritative items and tracking metadata | Browser + server | Persisted order conversion UUID; same name/ID and server values in both channels; still **unpaid**, payment due on delivery |
| Purchase — manual transfer | Trusted backend/admin changes an integrated, noncancelled order's `payment_status` to `paid`; item sum must equal order amount | Server | Same persisted conversion UUID on every attempt; initial unpaid submission sends no Purchase |
| Consultation | Accepted into `contact_messages`, including its booking details | None | No advertising event or consultation/health fields sent to Meta |

Pixel is intentionally suppressed on login, signup, account, order-lookup pages and URLs with unapproved parameters. Pixel reads the actual browser URL, so this avoids leaking order references, search terms and authentication parameters. Only validated product `id` and actual `fbclid` parameters are permitted. Server source URLs are fixed origin + `/checkout.html` or `/contact.html`, with no query strings. There is no SPA in this project; a future SPA must explicitly call the centralized tracking hooks after rendering its routes.

Browser one-action guards and session storage prevent repeated receipt emissions. Database request keys are scoped to a signed session and retained across lost-response retries and refreshes. Different confirmed actions get new keys. While a request's outcome is unknown, changing its details cannot silently create a second order. PostgreSQL transactions, per-session advisory locks, unique keys, an order-specific conversion ID and worker leases provide persistent idempotency. This is at-least-once network delivery with stable Meta deduplication identifiers, not an impossible promise of exactly-once HTTP delivery.

## Server, delivery and privacy behavior

`api/commerce.js` validates methods, JSON size/content, same-origin requests, signed HttpOnly/SameSite session cookies, CSRF tokens, product IDs, quantities, fields and payment method. A persistent rate bucket limits repeated submissions. Database mutations use server-only service credentials and service-only RPCs. `002_protect_order_writes.sql` blocks direct browser writes to orders, items and products; approved separate admin users can be allowlisted without bypassing existing RLS.

`hanaz_submit` writes order/header/items atomically. It rejects changed prices instead of silently charging a different amount. The browser's expected total is only a consistency check. A durable outbox stores business events before responding. Meta HTTP calls occur only in the worker and cannot cause checkout to fail. Failed item insertion rolls back the header and conversion job together.

The worker uses API **v26.0**, bearer authorization, seven-second HTTP timeouts, batches of five, leased jobs, at most six attempts and exponential backoff capped at one hour. Transient/network/429/5xx failures retry; permanent errors stop. Retries expire after 24 hours, within the browser/server deduplication window. Do not manually replay expired or sent events with new IDs. Job dataset and test/live mode are persisted; changing deployment mode cannot release queued test events into live reporting.

Email is trimmed/lowercased and SHA-256 hashed; Pakistan phone numbers are normalized to country-code digits before hashing. Original phone representation is retained in the order record for compatibility with existing lookup behavior. Valid `_fbp`/`_fbc` cookies, user agent and observed IP are unhashed; missing values are omitted, never invented. Names, addresses, consultation details, age, gender, messages and subject lines are not sent to Meta. Browser request storage contains a one-way payload digest and random key, not raw form fields. Completed/suppressed jobs discard matching fields; terminal matching data is also pruned during worker cleanup. Order records remain business records.

Consent is default-off. Decline immediately stops browser tracking and revokes the server's pending jobs once received. Business requests also carry the current consent choice as a narrowing condition; they cannot grant permission over a server decline. Revocation is retried after connectivity returns. A request already in flight to Meta cannot be recalled, and the server cannot learn an offline revocation until it is delivered. The UI reports a failed save rather than claiming the server received it.

See `browser-results.json` for the exact final results.

`tests/commerce.test.cjs` runs actual PostgreSQL SQL through PGlite against a fixture schema derived from the supplied frontend contract. It verifies atomic rollback, authoritative prices, duplicate request keys, payment-state transitions, consent, same-name/same-ID payloads, worker claims and retries, cancelled-order retries, mode isolation, exhausted retries, public-role write protection, rate limits, CSRF/origin/method/body validation, hashing and Meta transport failures. Its concurrent Promise submissions share PGlite's connection: true multi-connection PostgreSQL concurrency remains a staging check. Passing this fixture does not prove compatibility with an unseen production schema.

Live Supabase Auth completion, existing lookup RPC behavior against actual orders, independent admin operation, Vercel runtime routing/cron, native payment-provider webhook signatures (no such integration supplied), Meta SDK network behavior, account-side rules, actual deduplication and Diagnostics remain unverified. Local tests inspect generated browser calls and outbox payloads; they do not claim Meta received or deduplicated them. Mock API acceptance is not end-to-end Meta verification. CDN fonts/remote resources are deliberately blocked in screenshots; fixture product imagery is illustrative of layout, not a production catalog certification.

To reproduce locally: install the audit root's development dependencies with `npm ci`; run `node --test tests/commerce.test.cjs`; start `tests/preview.cjs` with `PORT=4174`; run `node tests/browser.cjs`; inspect the saved `static-audit.json` (the original archive check is not runnable against the modified repository baseline). The browser suite currently uses installed Chrome's Windows path. Never deploy `tests/` or the local preview.

## Small CTA/usability changes

- Quantity and remove controls have 44px minimum targets; visible keyboard-focus outlines and cart status announcements improve access without changing the brand palette/layout.
- Duplicate-submit locks, loading states and recoverable errors keep customers informed and preserve their cart/request after uncertainty.

- Consultation and newsletter feedback follows a successful database commit; failures stay on the form. Requests use the existing contact-message inbox, not a newly invented email/CRM integration.
- Direct product pages resolve their actual UUIDs; the legacy serum URL and certificate link reach the same intended product. Repeated PDP quantity/accordion initialization is guarded.
- Privacy choices use the existing button styles; no reviews, urgency, discounts, shipping promises or guarantees were invented.

Existing broad trust claims and star ratings were preserved, not independently substantiated. Recommendations rather than changes: verify those claims with their owner, review mobile first-screen product CTA placement using real catalog imagery, and improve nonfunctional placeholder/footer destinations after confirming their intended pages. A major redesign is not needed for this tracking repair.

## Rollback

For tracking-only rollback, set `META_ENABLED=false` and redeploy; stop the worker scheduler. Leave the repaired checkout, records and idempotency ledgers in place. This is the preferred rollback because orders continue working and old tracking defects are not reintroduced.

For emergency full-source rollback, disable delivery first, retain a database backup, run `database/rollback-hooks.sql` to remove only the new triggers, and restore the original website/deployment together. Preserve all business records and `hanaz_*` ledgers for reconciliation; do not delete or reset event IDs. Review any queued events before re-enabling delivery. Restoring the original checkout also restores its known browser-controlled pricing/non-atomic write behavior and old Purchase rule, so keep old Pixel snippets disabled until the incident is resolved. Existing JS caches require versioned URLs/cache invalidation during rollback as during release.
